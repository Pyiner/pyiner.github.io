Auto Research 流程、数据模型与提示词

这页不是在讲“理想中的 Auto Research”，而是在整理当前 GaryBot 实现里真正存在的三层结构： loop 流程、 durable 数据模型、 worker / verifier 提示词设计。 目的是把现在这套系统讲清楚，方便直接发链接讨论。

整体概览

Auto Research 不是“把用户问题丢给一个大 prompt 然后等回复”，而是一个有 durable run state、明确 work/verify 边界、可回看 candidate 历史、可重验证、可被 budget 和 provider health 打断的 bounded loop。

运行流程

下面这条线是当前 gateway 实现里的真实顺序，不是抽象流程图。 每一步都对应到具体 thread 命名、持久化节点和 verifier contract。

1

创建 Run，先把请求规范化到 ResearchSpec

用户传进来的 task / definition / definition_lines 会先归一化成 goal / dimensions / context / scope_paths / time_budget_secs / max_iterations。 后续 loop 直接消费的是 research_spec。

2

每轮先检查终态、预算、provider 健康度、pending reverify

Loop 进入每次迭代时，会先判断 run 是否已经终止、时间预算是否耗尽、同 workspace 是否刚发生 transport failure。 如果当前有 reverify 请求，会优先走 reverify 分支，而且不消耗 iteration 数。

3

Researching：构造 Worker Prompt，跑 Work Thread

Worker prompt 会注入当前 spec、反馈、search signal、best candidate、 candidate 历史压缩摘要，以及按预算百分比分出来的策略模式。 Work thread 形状是 thread::auto-research::{run_id}::work::{iteration}。

4

先把 Work 产物落盘，再进入 Verify

Worker 产出的 candidate result 会先以 “work_completed_pending_verify” 的状态写进 iteration。这样 verify 阶段即使失败，这轮 work 产物也不会丢失。

5

Judging：构造 Verifier Prompt，强制提交 MCP Verdict

Verifier thread 形状是 thread::auto-research::{run_id}::verify::{iteration}。 当前实现不接受 verifier 在聊天里手写 JSON；必须通过 auto_research_verdict 工具提交结构化 verdict。

6

记录 Candidate，更新 Best，写回 SearchSignal

每轮 verify 成功后会生成一个 Candidate， 挂上 Verdict。 接着更新全局最优、计算 convergence / regression，再把 search_signal 写回 run，供下一轮 worker prompt 使用。

7

继续下一轮，或进入终态

终态可能来自 budget、blocked、user stop，也可能来自 loop 完成。 当前实现里模型层保留了 legacy 的 passed， 但 loop 正常跑完后也会落到 completed。

状态机

产品层常说 queued → researching → judging → passed / blocked / budget_exhausted， 但当前模型实际上是下面这组状态。

Queued 待执行

Run 已创建，还没进入任何 worker/verifier 实际运行。

Researching 工作中

Worker 正在产出这一轮可验证的 candidate。

Judging 验证中

Verifier 正在对当前 candidate 做结构化打分与反馈。

Completed / Passed 正常终态

当前实现里两者都存在，其中 Passed 主要是 legacy 兼容。

Budget Exhausted 预算耗尽

直接受 time_budget_secs 的 wall-clock deadline 控制。

Blocked / UserStopped 被阻断

包括 provider transport failure、用户主动停止、网关重启等情形。

数据模型

这一层决定了 UI 能看见什么、loop 能记住什么、下一轮 prompt 能拿到什么。 重点在于字段职责，不只是字段名。

AutoResearchRun

Run 是 durable 根对象，承载任务、预算、candidate 历史、search signal 以及用户选中的 candidate。 

type AutoResearchRun = {
  run_id: string;
  state: 'queued' | 'researching' | 'judging'
       | 'passed' | 'completed'
       | 'budget_exhausted' | 'blocked' | 'user_stopped';
  task: string;
  definition: string;
  definition_lines: string[];
  browsing_allowed: boolean;
  file_edits_allowed: boolean;
  output_type?: string;
  max_iterations: number;
  time_budget_secs: number;
  iterations_used: number;
  terminal_reason?: string;
  search_signal?: SearchSignal;
  research_spec?: ResearchSpec;
  candidates: Candidate[];
  selected_candidate?: string;
};
  • research_spec 才是 loop 真正消费的规格对象。
  • provider_metadata 创建时可传，但只保存在执行内存里，不暴露给读接口。
  • selected_candidate 仍兼容旧的数字索引序列化。

ResearchSpec

这是当前设计里最重要的“单一事实来源”。如果要读懂 prompt，先看它。 

type ResearchSpec = {
  goal: string;
  dimensions: string[];
  context?: string;
  scope_paths: string[];
  time_budget_secs: number;
  max_iterations: number;
};
  • goal 决定 worker 与 verifier 的共同北极星。
  • dimensions 会直接映射到 verifier 的 dimension_scores。
  • scope_paths 会显式进入 worker prompt 作为改动范围约束。

AutoResearchIteration

Iteration 是“这一轮发生了什么”的记录层，不是完整 loop 内存镜像。 

type AutoResearchIteration = {
  run_id: string;
  iteration_index: number;
  state: 'researching' | 'judging' | 'completed';
  work_thread_id?: string;
  verify_thread_id?: string;
  research_plan?: string;
  candidate_result?: string;
  judge_verdict?: unknown;
  started_at: string;
  completed_at?: string;
};
  • UI 主要靠它呈现每轮摘要与判定结果。
  • work 结果会比 verify 更早落盘，确保 crash safety。

Candidate / Verdict

Candidate 是搜索空间里的候选解；Verdict 是 verifier 施加的结构化质量边界。 

type Candidate = {
  candidate_id: string;     // c_1, c_2, ...
  iteration: number;
  commit_sha?: string;
  branch?: string;
  approach_summary: string;
  based_on?: number;
  verdict?: Verdict;
  duration_secs: number;
};

type Verdict = {
  overall_score: number;    // 0..10
  dimension_scores: {
    dimension: string;
    score: number;
    evidence: string;
  }[];
  vs_best?: string;
  strengths: string[];
  weaknesses: string[];
  suggestions: string[];
};
  • overall_score 和 dimension score 都要求在 0..10 范围内。
  • vs_best 不是可选摆设，它体现了“当前 candidate 和历史最优比如何”。

SearchSignal

SearchSignal 不描述单个 candidate，而描述整个搜索轨迹是不是已经陷入收敛或退化。 

type SearchSignal =
  | {
      kind: 'converged';
      best_score: number;
      last_scores: number[];
    }
  | {
      kind: 'regressing';
      prev_avg: number;
      curr_avg: number;
    };
  • 近 3 个 candidate 都离 best 很近，会触发 converged。
  • 后 3 个均分明显低于前 3 个，会触发 regressing。

Thread 形状

当前 loop 是强线程化的，这让 debug、重放、权限控制都更清晰。 

work:
thread::auto-research::{run_id}::work::{iteration}

verify:
thread::auto-research::{run_id}::verify::{iteration}

reverify:
thread::auto-research::{run_id}::reverify::{candidate_id}
  • Verifier thread 会被授权调用 auto_research_verdict。
  • 这也是为什么 gary debug 能精确追踪整个 loop。

提示词

当前 Auto Research 的 prompt 不是“一个大总 prompt”，而是 Worker 与 Verifier 两套不同 contract：前者负责搜索和产出，后者负责工具化评审。

Worker Prompt：让每轮都处于“有限搜索 + 明确反馈”的局部状态

Worker prompt 的关键不是“描述任务”，而是把模型放进一个带预算、带 best candidate、带失败反馈、带搜索信号的局部决策场景。

Explore
< 40% budget

尝试完全不同的方法，不要顺着旧 candidate 小修小补。

Mix
40% ~ 70%

允许在“继续打磨”和“换方向”之间折中。

Exploit
>= 70%

预算快用尽时，优先修 best candidate 的 weaknesses。

You are Gary's Worker Agent (Auto Research loop).

Goal:
{goal}

Evaluation dimensions:
{dimensions}

{context}
{scope}
{feedback}
{signal}
Iteration: {iteration} of {max_iterations} ({budget_pct}% budget used)

{best_info}

STRATEGY: {strategy}

Previous candidates tried (avoid repeating approaches):
{previous_candidates}

Instructions:
- Produce a concrete candidate solution...
- Do not ask the user follow-up questions...
- Return concrete progress...
- Keep the answer concise, concrete, and implementation-grounded.
- Summarize your approach at the top (1-3 sentences).
  • Human Guidance 会直接插入 prompt，并要求优先遵守。
  • search_signal 会在 prompt 里显式提醒“收敛”或“退化”，迫使 worker 调整方向。
  • best_info 会带当前 best candidate 的分数与 weaknesses 摘要。
  • 历史 candidate 不会无限膨胀，而是压缩成得分分布、Top 3、Recent 2 和 omitted one-liner。
Candidate context compression:
- score distribution summary
- top 3 scored candidates
- recent 2 candidates
- omitted display cap = 10
- top weaknesses cap = 3
- each weakness cap = 200 chars

Verifier Prompt：只接受 Tool Verdict，不接受 text JSON fallback

Verifier 在当前实现里不是“点评员”，而是带工具约束的结构化判官。它的主要职责不是写分析，而是提交正确的 verdict payload。 

You are Gary's Verifier Agent (Auto Research loop).

Evaluate the candidate strictly against the goal and evaluation dimensions.
Submit the verdict by calling the `auto_research_verdict` MCP tool exactly once.
Do not hand-write the verdict in the chat response.
Do not narrate your analysis or add a prose summary before or after the tool call.
Your visible response should be the tool call itself; after a successful tool submission, stop.
Use these fields in the tool call:
  overall_score
  dimension_scores
  vs_best
  strengths
  weaknesses
  suggestions
If the tool returns an error, inspect the tool result, correct the arguments,
and retry the tool call.
Do not switch to text JSON or treat text JSON as a valid fallback path.

Goal:
{goal}

Evaluation dimensions:
{dimensions}

{best_comparison}

Candidate to evaluate:
{candidate}
  • Gateway 在 verifier run 结束后会先尝试取 tool-submitted verdict。
  • 如果只有文本输出、没有 MCP verdict，当前实现会直接报错，不采信 text JSON。
  • 这也是为什么 verifier prompt 里会反复强调“不要手写 verdict”。

Prompt 设计依赖 Runtime 约束，不是孤立文本

Prompt 有效，是因为它背后有持久化、线程命名、provider health 与 reverify 逻辑撑着；单独把 prompt 拿出来并不能还原当前 Auto Research。

  • Worker 结果先持久化，再 verify，避免 verify crash 时丢掉 work。
  • Reverify 会重算全局 best，而不是只看当前 candidate。
  • Search signal 在 candidate + iteration 写回前就会被计算并落盘。
  • Provider health preflight 会阻止已知坏状态反复重试。
create run
  → normalize spec
  → build worker prompt
  → execute work thread
  → persist work result
  → build verifier prompt
  → submit MCP verdict
  → update candidates
  → compute search signal
  → continue / stop / reverify

控制信号

这些机制决定了 loop 为什么会停、为什么会换策略、为什么 verifier 不能偷偷降级成自由文本。

Wall-clock Budget

当前 budget 是基于 created_at + time_budget_secs 计算出的 deadline，不是单纯的“最多跑几轮”。

First Progress Timeout

Provider run 如果在设定时间内连第一个 progress event 都没有，会被判定为 stalled。

Heartbeat Timeout

不只是起步要有进展；如果后续长时间没有任何 event，也会被视为 provider 停摆。

Provider Cooldown

同 workspace 最近若有 transport failure，会触发冷却期，阻止继续 live loop。

Search Signal Feedback

收敛和退化信号不会只留在日志里，而是会直接反馈到下一轮 worker prompt。

Reverify Path

Reverify 是独立于正常迭代的控制入口，用来重新判定某个 candidate，而不是额外消耗一个正常 iteration。
