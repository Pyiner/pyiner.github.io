运行元数据

状态 completed / budget_exhausted

输出类型 report
边界 不允许浏览；不允许改文件

Definition of Done

  1. 只允许输出 6 行，不要任何额外说明。
  2. 六行前缀必须依次是：标题：、目标：、证据一：、证据二：、证据三：、收尾：。
  3. 标题行必须同时包含 GaryBot 和 AutoResearch。
  4. 目标行必须同时包含“五轮”和“持续收敛”。
  5. 证据一行必须提到 garybot-gateway，并明确它负责 HTTP API 或 MCP。
  6. 证据二行必须提到 garybot-router，并明确它负责线程或 transcript。
  7. 证据三行必须提到 desktop/gary-desktop，并明确它负责桌面端或 Mac App。
  8. 三条证据行都必须各自以不同的来源标记结尾，且只能从 [docs/architecture.md]、[docs/agent/runtime-map.md]、[docs/auto-research.md] 这三个来源里选。
  9. 收尾行必须同时包含“适合演示”和“更稳”。
  10. 全文必须是中文说明；除了 GaryBot、AutoResearch、代码标识和来源标记外，不允许额外英文句子、阿拉伯数字或项目符号。
  11. 语气必须像对外演示文案，不要写成开发说明。

为什么这个命题适合 Demo

  • 它不是只有唯一正确答案的确定性任务，而是一个明显带优化空间的开放题。
  • 评分维度全都显式写出来，Verifier 很容易稳定给出结构化反馈。
  • 内容质量和格式约束可以同时拉扯，天然适合演示“越来越接近，但还没完全通过”的过程。
  • 这次真实运行最后就收敛到同一个剩余问题：正文前总会多出策略说明。

Verifier 焦点如何变化

  • 第 1 到第 2 轮：连结构化 verdict 都不稳定，重点还是“先把问题说清楚”。
  • 第 3 轮：第一次清晰指出，主体六行其实已经大体合格。
  • 第 4 到第 5 轮：焦点完全收缩到同一个剩余缺陷，不再分散。

稳定残余缺陷

这五轮最有价值的地方，不是分数从零散到 7.8，而是 verifier 持续把失败原因压缩到了同一个点： 答案前的说明块始终没有被真正删除。

现场讲解抓手

  • 先展示它很快就能做出“主体内容”。
  • 再展示 verifier 如何把问题逼到一个单点。
  • 最后强调：开放题的价值不在一次答对，而在持续逼近更优。

这页最终想帮你讲清楚什么

不是“它会不会做”，而是“它如何逼近更优”
对外表达

AutoResearch 不是只适合判断题，它更适合那些需要反复打磨、逐步逼近更优结果的任务。 在这类开放性问题里，生成端不断逼近目标，验证端不断攻击剩余缺陷， 最后得到的是一个可以解释的收敛过程，而不只是一个看起来“差不多”的答案。

这次 Demo 的一句话落点

  • 前两轮先把答案主体做出来。
  • 第三轮开始进入可解释收敛。
  • 第四、五轮不是乱改，而是围绕同一个残余问题持续对抗。
  • 最后失败也不是整体不行，而是只差一个明确到不能更明确的格式错误。
